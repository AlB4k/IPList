# IPList 1.4.0 Implementation Plan

> **For implementation:** Use `superpowers:executing-plans` and complete the tasks in order because the data model, matcher, migration, and UI depend on each other. Use separate agents only for explicitly requested, independent review work. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a lossless, updateable service catalog for all export modes, add Aeroflot and other catalog services through general metadata matching, and safely generate or enrich AmneziaWG `.conf` files without duplicated routes.

**Architecture:** The app will load a licensed service catalog, reuse a bundled/cached enrichment snapshot, refresh only stale DNS and ASN evidence within a bounded deadline, and match that evidence against the three existing address sources. Lite/Full source networks are partitioned at evidence boundaries so a service owns only the identified intersection; the remainder stays in a visible unassigned bucket. The union is proved equal to the source as an IP set. Export formatting and `.conf` editing use a standalone CIDR engine so selection, deduplication, subtraction, and validation share one tested implementation.

**Tech Stack:** Swift 5.9, SwiftUI, Foundation `URLSession`, Darwin resolver APIs, RIPEstat JSON API, existing standalone Swift test harness, macOS 13+.

**Spec:** `docs/superpowers/specs/2026-09-19-service-catalog-and-amneziawg-export-design.md`

## Global Constraints

- Release version is `1.4.0`; minimum supported macOS remains `13.0`.
- No external Swift dependencies.
- All three upstream address lists and the metadata catalog update in one validated transaction.
- A failed or suspicious update must preserve the last successful catalog, selections, profiles, and exports.
- Every Lite/Full source route must remain represented by a service or the selected-by-default unassigned bucket.
- Existing manual addresses, groups, notes, history, schedule, and profiles must survive migration.
- `.vpn` files are not read, modified, or exported.
- Independent `.conf` connections remain independent files; batch enrichment produces one output per input.
- User configuration secrets are processed only in memory and never logged or persisted by IPList.
- Runtime catalog input has explicit byte, item-count, string-length, CIDR-fragment, concurrency, and wall-clock limits.
- System DNS is used by default; IPList does not bulk-send catalog domains to Google or Cloudflare.

Initial defensive limits are centralized constants, covered by boundary tests, and documented: 4 MiB per catalog/list response, 2,000 services, 20,000 domains, 512 UTF-8 bytes per text field, 250,000 generated CIDR fragments, 8 concurrent enrichment requests, 12 seconds per request, and 60 seconds for the complete refresh. A warm-cache refresh is expected to finish within 30 seconds on the release test machine. Limits may be raised only with a recorded fixture and regression measurement.

## Review Focus

- CIDR containment, intersection, exact subtraction, and adjacent-network collapse must never widen the selected address set.
- Lite/Full attribution must split broad source ranges at evidence boundaries; assigning an entire containing range from one `/32` match is forbidden.
- Shared routes must remain exported while any owning service is selected.
- A partial DNS/RIPE outage must reuse cached enrichment instead of silently deleting routes.
- Existing `.conf` formatting and all non-`AllowedIPs` bytes must remain unchanged, including CRLF files and AWG 3 keys.
- Migration from a partially selected 1.3.x catalog must preserve deliberate choices while keeping every new service visible.
